Re-skinning a shipped console without touching its behaviour

A live freight-brokerage console on UAT: framework-free JavaScript inside a Next.js shell, thirty-five modules, guard tests that pin its markup. The brief was cosmetic only, nothing functional, nothing that could break production. This is what the design system and its skill found, fixed and proved, page by page.

Context

The build, the brief, the constraints

The build

The AIXFreight broker console: a Next.js 15 shell that boots a framework-free static console (sidebar, seven views, modals, live-call surfaces) written as plain JavaScript modules that coordinate through window. One 205 KB stylesheet holds every token, including a dark theme switched on data-theme. Backend guard tests assert literal strings in the frontend files, so markup, class names and even one grid track list are pinned.

The brief

Review every page and popup on the UAT workspace and log one to-do per flaw with page, steps, expected vs actual, severity and a screenshot. Then improve the UI using the design system. Screens only: the console dials real phone numbers, so no campaign or call could be started during the review.

The constraints

Minimal, cosmetic changes. No functionality touched, no production risk. The product owner reviews and merges; nothing goes to staging from the review branch. Every edit had to go through the repository's own engineering-agent rules and keep its guard tests green.

Method

Six steps, all scripted, all repeatable

The skill's definition of done asks for light and dark at three widths, no clipped text, every state handled, contrast and focus checked. Doing that by eye across ninety-seven screens is unreliable, so each step became a script.

Level the branch with UAT

UAT ran the staging branch, 95 commits ahead of the review branch. Staging was merged in first so every fix sits on the code users actually see.

Capture every screen

Playwright signs in, walks each hash route and popup, answers discard confirms, and takes tall screenshots at 1280 in both themes plus 768 and 390. Nothing that launches, saves, deletes or dials is ever clicked.

Review against the skill

Each capture was read against the skill's non-negotiables: text never overflows, one orange call to action, semantic tokens only, every state handled, 4.5:1 contrast, visible focus. Eight layout flaws came out of this pass.

Measure what eyes miss

A second script measured every visible text node's contrast in both themes, hovered every interactive element and compared computed styles, tabbed through every control, and logged failing network calls. That found the token-level problems.

Fix through the repo's own rules

Three passes, each an exact spec handed to the repository's console engineer agent: layout, then shell pages and empty states, then contrast, hover and focus. Guard tests decided the shape of two fixes.

Prove it and publish

Type-check, build, guard functions called directly (no database on the review machine), and the live DOM of each screen re-rendered offline with the new stylesheet to measure before and after. Findings went to the tracker as one to-do per flaw.

Verification & what stayed open

Proof, and the honest gaps

How it was proved

  • npx tsc --noEmit and npm run build pass; node --check on every edited console script.
  • No database on the review machine, so every guard module that reads the touched files was loaded directly and its test functions called: 542 pass; the failures are tests that need Postgres or a fixture, plus one guard that was already red on staging.
  • Two guards shaped the work: one requires exactly eight track tokens on the transactions grid line, another pins its literal ratio string. The fix respected both instead of editing them.
  • The production build was started locally without a backend to photograph the 404 page (real HTTP 404) and the splash handing over to the login screen.
  • The product owner was asked to run the full suite and the Playwright end-to-end specs before merging.

Left for product and backend decisions

  • The New Campaign dialog stays open when you navigate with the sidebar.
  • The transcript tab shows a server-error card for calls that were never answered; it should be an empty state.
  • A raw status enum ("COMPLETED_CALL") is shown next to the status.
  • Campaign filter labels sit off their controls; one page has two names; an unlabelled "0" badge in Add Agent.
  • Admin page loads fire 403 and 404 API calls; the theme-contrast guard is red on staging for a co-brand chip.
  • The "Heard at" final-rate link could not be reviewed: no call in the workspace had a captured final rate.
